## Descripción

### Problema/Requerimiento

Implementar el módulo de actividades (ContactActivities): (1) creación de una actividad asociada a un contacto, con activityType 'call' | 'meeting' | 'email', activityDate y description opcional; (2) búsqueda de actividades por contacto y tipo de actividad específico, retornando nombre, apellido, email y fecha de nacimiento del contacto junto con las actividades.

### Comportamiento Actual

- Existe la tabla ContactActivities en el schema (AC-002) y el módulo de contactos (AC-003). No hay endpoints para actividades.

### Comportamiento Esperado

- POST para crear actividad: body con personId, activityType ('call' | 'meeting' | 'email'), activityDate, description (opcional). 201 Created, 400 si validación falla, 404 si personId no existe.
- GET para búsqueda por contacto y tipo: query params personId (o :id en ruta) y activityType; respuesta 200 con lista de actividades y datos del contacto: firstName, lastName, email, dateOfBirth (según objetivo.md).
- Verbos HTTP y status codes correctos; DTOs con class-validator.

## Criterios de Aceptación

1. [ ] Creación de actividad: POST con personId, activityType, activityDate, description (opcional). activityType solo 'call' | 'meeting' | 'email'. 201 con actividad creada, 404 si persona no existe, 400 si validación falla.
2. [ ] Búsqueda por contacto y tipo: GET con personId (o :id) y activityType; 200 con lista de actividades y para cada resultado (o en cabecera) los datos del contacto: firstName, lastName, email, dateOfBirth.
3. [ ] Validación de activityType: rechazar valores distintos de 'call', 'meeting', 'email' con 400.
4. [ ] activityDate y description según schema (TEXT; description opcional).

## Detalles de Implementación

### Consideraciones Técnicas
- Formato de respuesta de búsqueda: puede ser { contact: { firstName, lastName, email, dateOfBirth }, activities: [...] } o array de ítems con datos de contacto + actividad. Objetivo.md pide "retornando: Nombre, Apellido, Email, Fecha de nacimiento" (del contacto); interpretar como incluir esos datos en la respuesta.
- activityDate: almacenar como ISO string o tipo fecha según schema (TEXT en objetivo.md).
- Consultas parametrizadas; índices en personId y activityType si hay muchos registros.

### Dependencias
- Depende de: AC-002 (schema ContactActivities), AC-003 (existencia de Person).
- Bloquea: AC-006 (Swagger documentará estos endpoints).

## Testing

### Escenarios de Prueba
1. Crear actividad con activityType 'call', 'meeting', 'email' y verificar 201 y persistencia.
2. Crear actividad con activityType inválido → 400.
3. Crear actividad con personId inexistente → 404.
4. Búsqueda por contacto y tipo: verificar que retorna actividades y datos del contacto (firstName, lastName, email, dateOfBirth).
5. Búsqueda sin resultados → 200 con lista vacía (o 404 según criterio de diseño).

### Casos Edge a Considerar
- description vacía o null (opcional).
- activityDate en el pasado (aceptar; no validar "solo fechas futuras" a menos que se exija).
