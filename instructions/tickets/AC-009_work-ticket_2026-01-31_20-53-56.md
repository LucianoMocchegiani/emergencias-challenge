## Descripción

### Problema/Requerimiento

El objetivo (docs/objetivo.md) no exige CRUD de PhoneType ni crear tipos previamente por API; la tabla `phone_type` existe en el schema pero puede estar vacía. Si está vacía, al crear un contacto con `phones` siempre se recibe 400 ("Tipo de teléfono con id X no existe"). Se necesita una **seed** que inserte tipos de teléfono iniciales (ej. móvil, casa, trabajo) para que quien use la API pueda crear contactos con teléfonos sin tener que tocar la BD a mano. Además, **aclarar en el README** que hay que ejecutar la seed (o que los contactos con teléfonos requieren tipos existentes en `phone_type`) y listar los tipos/ids iniciales.

### Comportamiento Actual

- La tabla `phone_type` se crea por TypeORM (synchronize) pero no se insertan filas por defecto.
- Quien arranca el proyecto y prueba POST /contacts con `phones` recibe 400 si no hay tipos en la BD.

### Comportamiento Esperado

- Existe una forma de cargar datos iniciales en `phone_type` (seed): por ejemplo tipos "móvil", "casa", "trabajo" con ids predecibles (1, 2, 3 si la seed se ejecuta en BD vacía).
- El README indica cómo ejecutar la seed y qué tipos/ids existen por defecto, para que crear contactos con teléfonos sea directo.

## Criterios de Aceptación

1. [ ] Existe una seed que inserta al menos los tipos de teléfono iniciales (ej. móvil, casa, trabajo) en la tabla `phone_type`.
2. [ ] La seed es ejecutable de forma repetible (ej. `npm run seed` o instrucción clara en README); si la tabla ya tiene datos, no duplicar (idempotente o documentar que se ejecuta solo en BD vacía).
3. [ ] El README explica cómo ejecutar la seed y lista los tipos/ids iniciales (o indica dónde verlos), y aclara que los contactos con teléfonos deben usar `phoneTypeId` existentes en `phone_type`.

## Detalles de Implementación

### Consideraciones Técnicas
- **Idempotencia:** La seed puede ser "solo insertar si no hay filas" o "INSERT OR IGNORE" / "ON CONFLICT" según enfoque (SQL vs script TypeORM). Si es SQL puro, el orden de ejecución (antes o después del primer arranque de la app) debe quedar claro.
- **Ruta de la BD:** TypeORM usa `process.env.DATABASE_PATH ?? './data/contacts.db'`; la seed debe usar la misma ruta para no escribir en otro archivo.
- **Sin CRUD de PhoneType:** Este ticket no pide endpoints para crear/listar tipos; solo datos iniciales y documentación.

## Testing

### Escenarios de Prueba
1. Ejecutar la seed (npm run seed o equivalente) y verificar que la tabla `phone_type` tiene las filas esperadas (ej. 3 tipos).
2. Arrancar la app, crear un contacto con `phones: [{ number: "...", phoneTypeId: 1 }]` y verificar 201.
3. Leer el README y verificar que se entiende cómo ejecutar la seed y qué tipos hay.

### Casos Edge a Considerar
- BD ya tiene tipos (seed no debe fallar ni duplicar si se hace idempotente).
- Primera vez: carpeta data/ o archivo contacts.db puede no existir hasta el primer arranque de la app; la seed puede ejecutarse después del primer start:dev o crear la BD si usa TypeORM/DataSource.
