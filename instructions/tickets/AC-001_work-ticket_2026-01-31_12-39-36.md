## Descripción

### Problema/Requerimiento

Se necesita planificar de forma generalizada la creación de tickets que dividan el trabajo del Backend Challenge (agenda de contactos). El objetivo es tener un plan de tickets que permita abordar cada parte del proyecto con su propio ticket y, a su vez, un plan de acción (action plan) por ticket, para ir enfocándose en cada tarea de forma incremental sin mezclar alcances.

### Comportamiento Actual

- Existe la especificación en `docs/objetivo.md` y las reglas en `instructions/` (work-ticket, action-plan, etc.).
- No hay aún un listado acordado de tickets que cubran todo el alcance del challenge.
- No hay un criterio explícito de cómo partir el trabajo en tickets (por operación, por módulo, por capa, etc.).

### Comportamiento Esperado

- Lista clara de tareas que serán tickets (AC-002, AC-003, …) a partir de docs/objetivo.md.
- Por cada tarea, ejecutar `@work-ticket.mdc` para generar el archivo de ticket en `instructions/tickets/`; no es necesario crear un archivo de planning aparte.
- `instructions/pending-tickets.md` actualizado automáticamente por cada ejecución de work-ticket.
- Flujo: para cada tarea → ejecutar work-ticket → luego action plan → implementación → PR.

## Detalles de Implementación

### Consideraciones Técnicas

- **Alcance por ticket:** Partir según operaciones de la API (crear contacto, búsqueda por email, etc.), por módulo NestJS (contacts, activities, phones, addresses), o por capa (schema DB, módulos, Swagger, tests). Definir una convención y mantenerla.
- **Dependencias:** El esquema de base de datos (SQLite) y el bootstrap de NestJS suelen ser previos a los endpoints de negocio; los tickets de “crear contacto” o “búsqueda por email” pueden ir después.
- **Orden sugerido:** 1) Proyecto NestJS + SQLite + schema; 2) Módulo contactos (CRUD + búsquedas); 3) Teléfonos y direcciones; 4) ContactActivities y búsqueda de actividades; 5) Swagger; 6) Tests y linter (o repartidos por ticket).
- **Documentación:** No se crea archivo de planning; la lista de tareas puede quedar en el action plan de AC-001. Solo se ejecuta `@work-ticket.mdc` por cada ticket.

### Dependencias

- Depende de: ninguno (es el primer ticket de planning).
- Bloquea: el resto de tickets de implementación (AC-002 en adelante) se crearán a partir de este planning.

## Testing

### Escenarios de Prueba

1. Revisar que el listado de tickets cubra todas las operaciones requeridas en `docs/objetivo.md` (crear contacto, búsquedas, edición, eliminación, actividades, etc.).
2. Verificar que cada ticket propuesto tenga un alcance claro y sea accionable con un solo action plan.
3. Comprobar que `pending-tickets.md` (o el documento de planning) esté actualizado y sea coherente con las reglas de `instructions/README.md`.

### Casos Edge a Considerar

- Si una operación es muy grande (ej: “módulo contactos completo”), subdividirla en varios tickets (ej: crear contacto, búsqueda por email, búsqueda por datos personales, etc.).
- Mantener consistencia con el prefijo AC-XXX y con la numeración en `pending-tickets.md`.

## Notas Adicionales

Este ticket es de tipo **Chore** y tiene prioridad **Alta** porque establece la base para el resto del trabajo: sin un planning claro de tickets, es más difícil dividir el esfuerzo y enfocarse en una tarea a la vez. Al completarlo, el equipo (o la IA) podrá generar los tickets AC-002, AC-003, etc., siguiendo el mismo formato y el orden/dependencias acordados.
