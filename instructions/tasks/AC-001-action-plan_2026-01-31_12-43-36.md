# AC-001 - Planificación generalizada: creación de tickets para dividir el trabajo

## Descripción de la Tarea

Definir un planning de tickets que divida el trabajo del Backend Challenge (agenda de contactos) en tareas acotadas. Cada tarea tendrá su propio ticket (AC-002, AC-003, …) y, a partir de ese ticket, un action plan específico para implementar de forma incremental.

**Comportamiento actual:**
- Existe la especificación en `docs/objetivo.md` y las reglas en `instructions/`.
- No hay un listado acordado de tickets que cubran todo el alcance.
- No hay criterios explícitos de cómo partir el trabajo en tickets.

**Comportamiento esperado:**
- Lista clara de tareas que serán tickets (AC-002, AC-003, …).
- Un archivo de ticket creado con `@work-ticket.mdc` por cada tarea (en `instructions/tickets/`).
- `instructions/pending-tickets.md` actualizado automáticamente por cada ejecución de work-ticket.
- Flujo: para cada tarea → ejecutar work-ticket → luego action plan → implementación → PR.

## Criterios de Aceptación

1. ✅/❌ Se definió la lista de tareas que serán tickets (AC-002, AC-003, …) a partir de docs/objetivo.md.
2. ✅/❌ Por cada tarea se ejecutó `@work-ticket.mdc` y se generó el archivo en `instructions/tickets/`.
3. ✅/❌ `instructions/pending-tickets.md` contiene todos los tickets creados (la regla work-ticket los añade al ejecutarse).
4. ✅/❌ Cada ticket tiene alcance acotado para poder tener después su propio action plan e implementación.

### Paso 3: Ejecutar @work-ticket.mdc por cada ticket

**Descripción:**
Por cada tarea de la lista del Paso 2, ejecutar la regla `@work-ticket.mdc` indicando el título y la descripción del ticket. Cada ejecución genera un archivo en `instructions/tickets/` (ej: `AC-002_work-ticket_[FECHA-HORA].md`) y actualiza automáticamente `instructions/pending-tickets.md`.

**Archivos a modificar/crear:**
- `instructions/tickets/AC-XXX_work-ticket_[FECHA-HORA].md` (uno por ticket, creados por la regla)
- `instructions/pending-tickets.md` (actualizado por la regla en cada ejecución)

**Detalles de implementación:**
- Para cada ticket: invocar `@work-ticket.mdc` y dar la descripción, por ejemplo:  
  *"Genera un ticket para: [título del ticket]. Descripción: [descripción breve]. Prioridad: [Alta/Media/Baja]."*
- La regla pide fecha/hora (Get-Date), genera el archivo en `instructions/tickets/` y añade la línea en `pending-tickets.md`.
- Repetir hasta cubrir todos los ítems de la lista del Paso 2.

**Notas:**
- No hace falta crear ningún archivo `planning-tickets.md`; solo ejecutar work-ticket por cada tarea.
- Orden recomendado: crear los tickets en el mismo orden en que se implementarán (AC-002, AC-003, …).

**Recursos útiles:**
- [instructions/work-ticket.mdc](../work-ticket.mdc)

### Paso Final: Generar Descripción del Pull Request

**Descripción:**
Una vez completados todos los pasos anteriores y verificada la implementación, genera la descripción completa del Pull Request usando la regla `@pr-description.mdc`.

**Comando a ejecutar:**
```
@pr-description.mdc
```

**Resultado esperado:**
- Archivo generado: `AC-001_pr-description_[FECHA-HORA].md` en `/instructions/prs/`
- El archivo contendrá una descripción completa del PR lista para copiar y pegar en Git
- Incluirá: título, resumen, motivación, cambios técnicos, testing, referencias y riesgos

**Notas:**
- Este paso se ejecuta DESPUÉS de completar toda la implementación (Pasos 1 a 4).
- La descripción se genera basándose en los cambios realizados (tickets en instructions/tickets/, pending-tickets.md actualizado).
- No editar manualmente a menos que sea estrictamente necesario.
