# AC-011 - Documentación del proyecto: docs/, diagrama BD, arquitectura, tecnologías, patrones y referencias en README

## Descripción de la Tarea

Crear y organizar la documentación del proyecto en la carpeta `docs/`: diagrama de base de datos completo (Mermaid), arquitectura con referencia a ADR, tecnologías y patrones con justificación, glosario e índice. Actualizar README raíz para referenciar toda la documentación y corregir src/contacts/README.md (GET /contacts/by-phone solo con number y phoneTypeId).

**Comportamiento actual:**
- README raíz enlaza a objetivo e instructions; no enlaza a docs/ ni a READMEs de módulos.
- No existe documentación estructurada en docs/ (solo docs/objetivo.md).
- No hay diagrama de BD completo con ContactActivities en formato reutilizable.
- No hay documento de arquitectura ni ADR, ni technologies/patterns/glossary.
- src/contacts/README.md documenta by-phone con typeName (desactualizado).

**Comportamiento esperado:**
- README raíz con sección Documentación que enlace a docs/README.md (índice) y a READMEs de contacts y activities.
- docs/ con README.md (índice), database-diagram.md, architecture.md, adr/, technologies.md, patterns.md, glossary.md.
- src/contacts/README.md con GET /contacts/by-phone documentado solo con number y phoneTypeId (obligatorios).

### Paso 2: Crear docs/database-diagram.md (diagrama ER completo)

**Descripción:**
Crear el archivo `docs/database-diagram.md` con un diagrama entidad-relación en Mermaid que incluya todas las tablas: Person, Phone, PhoneType, Address y **ContactActivities**. El diagrama debe ser claro, con atributos principales y relaciones (cardinalidades). Puede incluir una versión "más gráfica" si se desea (por ejemplo bloques por dominio).

**Archivos a modificar/crear:**
- `docs/database-diagram.md` (nuevo)

**Detalles de implementación:**
- Usar sintaxis Mermaid `erDiagram`.
- Person ||--o{ Phone : "tiene"; Person ||--o{ Address : "tiene"; PhoneType ||--o{ Phone : "clasifica"; Person ||--o{ ContactActivities : "tiene" (o similar).
- Incluir en cada entidad: id (PK), atributos principales según docs/objetivo.md. ContactActivities: id, personId (FK), activityType, activityDate, description.
- Opcional: breve párrafo introductorio indicando que es el modelo implementado (TypeORM/SQLite).

**Recursos útiles:**
- [Mermaid ER Diagram](https://mermaid.js.org/syntax/entityRelationshipDiagram.html)
- docs/objetivo.md (esquema parcial y tabla ContactActivities)

Crear la carpeta `docs/adr/` con un índice `docs/adr/README.md` y al menos un ADR (ej. `0001-stack-inicial.md`) que documente la decisión de usar NestJS + TypeORM + SQLite + Swagger. Formato ADR breve: título, contexto, decisión, consecuencias.

**Archivos a modificar/crear:**
- `docs/architecture.md` (nuevo)
- `docs/adr/README.md` (nuevo)
- `docs/adr/0001-stack-inicial.md` (nuevo, o nombre similar)

**Detalles de implementación:**
- architecture.md: descripción por capas; mención de NestJS modules, controllers, services, DTOs, TypeORM; enlace a "Las decisiones se documentan en [ADR](adr/README.md)".
- adr/README.md: lista de ADRs con número, título y enlace (ej. 0001 - Stack inicial).
- 0001-*.md: Contexto (necesidad de API REST, TypeScript, SQLite); Decisión (NestJS, TypeORM, Swagger, class-validator, Jest, ESLint); Consecuencias (positivas y negativas breves).

**Notas:**
- ADR puede ser conciso (una página). Si se prefieren varios ADRs (uno por tecnología o por decisión), crear 0001, 0002, etc., y listarlos en adr/README.md.
