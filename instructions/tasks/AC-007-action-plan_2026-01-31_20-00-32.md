# AC-007 - Tests (Jest) y linter (ESLint)

## Descripción de la Tarea

Configurar y aplicar tests unitarios con Jest (incluido en NestJS) y linter con ESLint para el proyecto. Incluye: verificar/ajustar la configuración de Jest para NestJS, añadir al menos tests unitarios para servicios críticos (ContactsService, ActivitiesService) con casos de éxito y error (404, 400), y asegurar que ESLint se ejecuta sin errores en el código existente. Durante la fase de tests, los bugs detectados se registrarán como tickets de corrección separados (ej. AC-008, AC-009) para corregirlos de forma trazable.

**Comportamiento actual:**
- El proyecto tiene Jest y ESLint configurados (package.json: `npm run test`, `npm run lint`; eslint.config.mjs con TypeScript y Prettier). Existe `app.controller.spec.ts` como stub. No hay tests unitarios para ContactsService ni ActivitiesService.

**Comportamiento esperado:**
- `npm run test` ejecuta los tests y al menos los tests de ContactsService y ActivitiesService pasan (casos de éxito y al menos un caso de error por módulo).
- `npm run lint` ejecuta ESLint y el proyecto queda sin errores de lint (o se documentan excepciones justificadas).
- Bugs encontrados durante la fase de test se documentan como tickets de corrección y se corrigen en PRs separados o en un paso explícito del plan.

## Criterios de Aceptación

1. ❌ `npm run test` ejecuta los tests y al menos los tests de servicios críticos (contactos y/o actividades) pasan.
2. ❌ Los tests cubren casos de éxito y al menos un caso de error (ej: 404, 400) por módulo crítico.
3. ❌ `npm run lint` (o equivalente) ejecuta ESLint y el proyecto queda sin errores de lint (o se documentan excepciones justificadas).
4. ❌ La configuración de ESLint es adecuada para TypeScript y NestJS (reglas recomendadas o estándar del ecosistema).

### Paso 3: Tests unitarios para ContactsService

**Descripción:**
Crear `src/contacts/contacts.service.spec.ts`. Usar `Test.createTestingModule` con ContactsService y mocks de los repositorios (Person, Phone, PhoneType, Address) vía `getRepositoryToken`. Implementar al menos:
- **create:** un test de éxito (DTO válido, personRepo.save devuelve entidad, se espera que el servicio devuelva el contacto creado).
- **create:** un test de error (ej. email duplicado → ConflictException, o phoneTypeId inexistente → BadRequestException "Tipo de teléfono con id X no existe").
- Opcional: **findByEmail** o **findOne** (éxito y 404 si no existe).

Los mocks deben devolver valores controlados (findOne, save, find) para no tocar la base de datos real.

**Archivos a modificar/crear:**
- `src/contacts/contacts.service.spec.ts`

**Detalles de implementación:**
- Importar ContactsService, ContactsModule (o las entidades y DTOs necesarios), getRepositoryToken de @nestjs/typeorm.
- Mock de repos: `{ provide: getRepositoryToken(Person), useValue: { findOne: jest.fn(), save: jest.fn(), create: jest.fn(), ... } }` (y lo mismo para Phone, PhoneType, Address si el servicio los usa en create).
- En el test de create éxito: configurar los mocks para que findOne (por email) devuelva null (no duplicado), save devuelva la entidad; llamar a service.create(dto) y esperar el resultado.
- En el test de error: configurar el mock para que falle la validación (ej. validatePhoneTypeIds o email duplicado) y esperar que se lance BadRequestException o ConflictException.

**Notas:**
- Al escribir estos tests pueden aparecer bugs (ej. que create persista el contacto antes de validar phoneTypeId y luego lance 400; el test de "no debe crear contacto si phoneTypeId no existe" fallaría hasta corregir el bug). Esos bugs se registran como tickets de corrección (Paso 5).

**Recursos útiles:**

## Consideraciones Técnicas

### Performance
- Tests unitarios con mocks deben ejecutarse rápido (sin I/O de base de datos). No usar SQLite real en tests unitarios para no ralentizar ni depender del estado del .db.

### Seguridad
- No aplica directamente; los tests no exponen datos reales.

### Casos Edge
- Email duplicado (ConflictException), contacto no encontrado (404), phoneTypeId inexistente (400), personId inexistente en actividades (404). Los tests deben cubrir al menos un caso de error por módulo crítico.
- Tests que dependen de BD: usar siempre mocks; no asumir que existe un contacto con id 1 en la base de datos.

### Compatibilidad
- Mantener compatibilidad con la configuración actual de Jest (rootDir src, testRegex .spec.ts) y ESLint (eslint.config.mjs) para no romper scripts existentes.

## Patrones de Código a Usar

- **Tests (Jest + NestJS):**
  - TestingModule con getRepositoryToken(Entity) y useValue con jest.fn() para mocks.
  - describe/it o test; expect(service.método()).resolves.toEqual(...) o expect(...).rejects.toThrow(NotFoundException).
  - Un archivo .spec.ts por servicio (o controlador) junto al archivo bajo test.
- **ESLint:**
  - No relajar reglas sin justificación; documentar excepciones si se desactiva algo en un archivo.
