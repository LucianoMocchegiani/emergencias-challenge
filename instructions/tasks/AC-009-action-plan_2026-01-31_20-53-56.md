# AC-009 - Seed de tipos de teléfono (PhoneType) y documentación en README

## Descripción de la Tarea

Añadir una **seed** que inserte tipos de teléfono iniciales (ej. móvil, casa, trabajo) en la tabla `phone_type`, un script ejecutable (ej. `npm run seed`) y **aclarar en el README** cómo ejecutar la seed y qué tipos/ids existen por defecto, para que crear contactos con teléfonos sea directo sin tocar la BD a mano.

**Comportamiento actual:**
- La tabla `phone_type` se crea por TypeORM (synchronize) pero no se insertan filas. Quien prueba POST /contacts con `phones` recibe 400 ("Tipo de teléfono con id X no existe") si la BD está vacía de tipos.

**Comportamiento esperado:**
- Existe una seed que carga tipos iniciales (móvil, casa, trabajo) y es ejecutable (ej. `npm run seed`).
- El README indica cómo ejecutar la seed y lista los tipos/ids iniciales; aclara que los contactos con teléfonos deben usar `phoneTypeId` existentes en `phone_type`.

## Criterios de Aceptación

1. ❌ Existe una seed que inserta al menos los tipos de teléfono iniciales (ej. móvil, casa, trabajo) en `phone_type`.
2. ❌ La seed es ejecutable de forma repetible (ej. `npm run seed`); si la tabla ya tiene datos, no duplicar (idempotente o documentar uso).
3. ❌ El README explica cómo ejecutar la seed y lista los tipos/ids iniciales; aclara que los contactos con teléfonos requieren `phoneTypeId` existentes.

## Pasos de Implementación

### Paso 1: Crear script o archivo de seed para PhoneType

**Descripción:**
Crear la seed que inserta tipos de teléfono iniciales. Opciones: (A) archivo SQL `database/seed.sql` con INSERTs, ejecutable con `sqlite3`; (B) script Node/TypeScript que use TypeORM DataSource (misma config que AppModule), compruebe si `phone_type` tiene filas y, si está vacía, inserte los tipos (móvil, casa, trabajo). La opción B es idempotente y usa la misma ruta de BD que la app. Si se elige A, documentar que la seed debe ejecutarse después del primer arranque de la app (para que la tabla exista).

**Archivos a modificar/crear:**
- `database/seed.sql` (si opción A) o `src/database/seed.ts` / `scripts/seed.ts` (si opción B)
- Si opción B: usar DataSource de TypeORM con la misma configuración (type: 'sqlite', database: process.env.DATABASE_PATH ?? './data/contacts.db', entities desde las entidades existentes). Insertar solo si `phone_type` está vacía (count === 0).

**Detalles de implementación:**
- Tipos a insertar: por ejemplo `móvil`, `casa`, `trabajo` (typeName). Los ids serán 1, 2, 3 si se insertan en BD vacía en ese orden.
- Idempotencia (opción B): `const count = await dataSource.getRepository(PhoneType).count(); if (count === 0) { await repo.save([{ typeName: 'móvil' }, { typeName: 'casa' }, { typeName: 'trabajo' }]); }`.
- Asegurar que la ruta de la BD sea la misma que en app (variable de entorno o default ./data/contacts.db).

## Consideraciones Técnicas

### Performance
- La seed se ejecuta una vez (o de forma idempotente); no impacta el arranque de la app si se corre como script aparte.

### Seguridad
- Sin cambios en la API; solo datos iniciales y documentación.

### Casos Edge
- BD no existe: documentar que se puede arrancar la app una vez (para crear la BD con synchronize) y luego ejecutar la seed, o que el script de seed maneje la creación si aplica.
- BD ya tiene tipos: seed idempotente (no insertar si ya hay filas) evita duplicados.
