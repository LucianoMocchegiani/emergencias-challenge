# AC-003 - Módulo contactos: creación, búsqueda por email, búsqueda por datos personales, edición, eliminación

## Descripción de la Tarea

Implementar el módulo de contactos (Person) en NestJS con las operaciones requeridas por docs/objetivo.md: creación de contacto, búsqueda por email, búsqueda por datos personales, edición de datos personales y eliminación de contacto. Usar verbos HTTP correctos y status codes apropiados.

**Comportamiento actual:**
- Existe el proyecto NestJS y el schema SQLite (AC-002), pero no hay endpoints de contactos.

**Comportamiento esperado:**
- POST para crear contacto (201 Created, 400 si validación falla).
- GET para búsqueda por email (200 con contacto, 404 si no existe).
- GET para búsqueda por datos personales (query params opcionales; 200 con lista).
- PATCH o PUT para editar datos personales por id (200, 404 o 400).
- DELETE para eliminar contacto por id (200 o 204, 404 si no existe).
- DTOs con class-validator; respuestas tipadas; status codes correctos.

## Criterios de Aceptación

1. ❌ Creación de contacto: POST con body validado; retorna 201 y el contacto creado.
2. ❌ Búsqueda por email: GET con query param email; 200 con contacto o 404.
3. ❌ Búsqueda por datos personales: GET con query params (firstName, lastName, dateOfBirth, email); 200 con lista de contactos.
4. ❌ Edición: PATCH/PUT por id; 200 con contacto actualizado, 404 o 400 según corresponda.
5. ❌ Eliminación: DELETE por id; 200/204, 404 si no existe.
6. ❌ Validación de entrada con DTOs; status codes correctos en todos los casos.

## Pasos de Implementación

### Paso 1: Instalar class-validator y class-transformer; habilitar ValidationPipe global

**Descripción:**
Añadir las dependencias class-validator y class-transformer al proyecto. En `main.ts` (o en el módulo raíz) registrar ValidationPipe global para que los DTOs se validen automáticamente y se devuelva 400 Bad Request cuando falle la validación.

**Archivos a modificar/crear:**
- `package.json` (dependencias)
- `src/main.ts` (ValidationPipe global)

**Detalles de implementación:**
- `npm install class-validator class-transformer`
- En `main.ts`: `app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true }));` (o opciones equivalentes para transformar y validar).

**Notas:**
- whitelist: true elimina propiedades no definidas en el DTO; forbidNonWhitelisted: true devuelve 400 si se envían propiedades extra (opcional, según preferencia).

**Recursos útiles:**

### Paso 3: Crear ContactsModule y ContactsService

**Descripción:**
Crear `src/contacts/contacts.module.ts` y `src/contacts/contacts.service.ts`. El módulo importa TypeOrmModule.forFeature([Person]) para inyectar el repositorio. El servicio inyecta Repository<Person> y expone: create(dto), findByEmail(email), findByPersonalData(filters), update(id, dto), remove(id). Eliminación física (delete) por defecto; CASCADE en FKs ya borra teléfonos, direcciones y actividades asociadas.

**Archivos a modificar/crear:**
- `src/contacts/contacts.module.ts`
- `src/contacts/contacts.service.ts`

**Detalles de implementación:**
- create: repository.save(dto) → retorna Person; si email único y ya existe, lanzar ConflictException (409) o BadRequestException (400).
- findByEmail: repository.findOne({ where: { email } }) → retorna Person o null; el controlador lanza NotFoundException si null.
- findByPersonalData: repository.find({ where: filtros opcionales }) con objeto where construido desde query params (solo incluir campos no undefined).
- update: repository.findOne por id; si no existe NotFoundException; repository.save({ ...person, ...dto }).
- remove: repository.findOne por id; si no existe NotFoundException; repository.remove(person).

**Notas:**
- Búsqueda por datos personales: permitir filtros opcionales (cualquier combinación de firstName, lastName, dateOfBirth, email). TypeORM where con Like o exacto según necesidad.

### Paso 4: Crear ContactsController con rutas REST

**Descripción:**
Crear `src/contacts/contacts.controller.ts` con base path `/contacts`. Rutas: POST / (crear), GET /email?email= (búsqueda por email), GET / (búsqueda por datos personales con query params), GET /:id (opcional, obtener por id), PATCH /:id o PUT /:id (editar), DELETE /:id (eliminar). Inyectar ContactsService; en cada ruta llamar al servicio y devolver status y body apropiados (201 + body en POST, 200 + body en GET/PATCH, 200 o 204 sin body en DELETE, 404 cuando corresponda).

**Archivos a modificar/crear:**
- `src/contacts/contacts.controller.ts`

**Detalles de implementación:**
- POST @Post() create(@Body() dto: CreateContactDto) → 201, body contacto creado.
- GET @Get('email') findOneByEmail(@Query('email') email: string) → 200 o 404.
- GET @Get() findAll(@Query() query: { firstName?, lastName?, dateOfBirth?, email? }) → 200 con array.
- PATCH @Patch(':id') update(@Param('id') id: string, @Body() dto: UpdateContactDto) → 200 o 404/400.
- DELETE @Delete(':id') remove(@Param('id') id: string) → 200/204, 404 si no existe.
- Usar ParseIntPipe o ParseUUIDPipe para :id si se usa número; validar que id sea número.

**Notas:**
- Ruta GET /email debe ir antes de GET /:id para que "email" no se interprete como id. O usar GET /?email= para búsqueda por email y GET /?firstName=... para búsqueda por datos.

**Recursos útiles:**
- [NestJS Controllers](https://docs.nestjs.com/controllers)

## Consideraciones Técnicas

### Performance
- Búsqueda por datos personales: usar where con los filtros enviados; la entidad Person ya existe y TypeORM usa consultas parametrizadas. Índice en email (si no existe, considerar añadirlo en entidad Person para búsqueda por email).

### Seguridad
- Validación de entrada con class-validator en DTOs.
- Consultas parametrizadas (TypeORM por defecto).
- No exponer mensajes internos en 500; usar mensajes genéricos si se capturan excepciones.

### Casos Edge
- Email duplicado en creación: definir 409 Conflict o 400 Bad Request (o permitir duplicados si el negocio lo permite).
- GET por email con email vacío: validar y devolver 400.
- PATCH con body vacío: permitir (no cambiar nada) o 400 según criterio.
- DELETE de contacto con teléfonos/direcciones/actividades: CASCADE ya los borra (AC-002).

### Compatibilidad
- Rutas REST alineadas con docs/objetivo.md; sin breaking changes para futuros tickets AC-004, AC-005.
