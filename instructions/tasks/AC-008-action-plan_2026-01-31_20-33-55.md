# AC-008 - ContactsService.create: validar phoneTypeId antes de persistir Person

## Descripción de la Tarea

Corregir el bug en `ContactsService.create`: cuando el DTO incluye `phones` con un `phoneTypeId` que no existe en `phone_types`, el servicio lanza 400 pero **ya persistió la Person**, dejando un contacto creado en la base de datos (inconsistencia). La solución es validar los `phoneTypeId` **antes** de guardar la Person.

**Comportamiento actual:**
1. Se valida que el email no exista.
2. Se crea y guarda la Person.
3. Si hay `phones`, se llama a `validatePhoneTypeIds`; si algún id no existe, se lanza BadRequestException.
4. El contacto ya está guardado cuando se lanza la excepción.

**Comportamiento esperado:**
- Si algún `phoneTypeId` no existe, **no** se debe persistir el contacto y se debe devolver 400.
- Validar `phoneTypeIds` **antes** de llamar a `personRepo.save(person)`.

## Criterios de Aceptación

1. ❌ Al crear contacto con `phones` que incluyen un `phoneTypeId` inexistente, se devuelve 400 y **no** se crea ningún registro en `person`.
2. ❌ Los tests unitarios existentes (AC-007) siguen pasando.
3. ❌ Opcional: test que verifique que `personRepo.save` no se llama cuando phoneTypeId es inválido.

## Pasos de Implementación

### Paso 1: Validar phoneTypeIds antes de persistir Person en create

**Descripción:**
En `ContactsService.create`, mover la llamada a `validatePhoneTypeIds` para que se ejecute **antes** de crear y guardar la Person. Así, si algún `phoneTypeId` no existe, se lanza BadRequestException sin haber llamado a `personRepo.save`.

Orden actual: (1) validar email, (2) create + save Person, (3) si phones → validatePhoneTypeIds, (4) save phones, (5) save addresses.  
Orden nuevo: (1) validar email, (2) **si phones → validatePhoneTypeIds**, (3) create + save Person, (4) save phones, (5) save addresses.

**Archivos a modificar/crear:**
- `src/contacts/contacts.service.ts`

**Detalles de implementación:**
- Dentro del método `create(dto: CreateContactDto)`:
  - Mantener la validación de email duplicado al inicio.
  - **Añadir** justo después (y antes de `personRepo.create`): si `dto.phones?.length`, llamar a `await this.validatePhoneTypeIds(dto.phones.map((p) => p.phoneTypeId))`.
  - Luego seguir con `personRepo.create(dto)`, `personRepo.save(person)`, y el resto (guardar phones, addresses) sin cambiar la lógica.
- No hace falta transacción: al validar antes de cualquier `save`, si falla la validación no se persiste nada.

**Notas:**
- El método `validatePhoneTypeIds` ya existe y lanza `BadRequestException` con el mensaje correcto; solo cambia el orden de ejecución en `create`.
- Las direcciones (`addresses`) no tienen validación de IDs externos en este ticket; solo phones.

**Recursos útiles:**
- Código actual: líneas 43–80 de `contacts.service.ts` (método create).

## Consideraciones Técnicas

### Performance
- Una llamada extra a `validatePhoneTypeIds` antes del save no añade un round-trip adicional si ya se iba a llamar después; solo se ejecuta antes. Misma cantidad de consultas a `phone_types`.

### Seguridad
- Sin cambios en validación de entrada; solo orden de ejecución.

### Casos Edge
- Si `dto.phones` es array vacío `[]`, no se llama a `validatePhoneTypeIds` (igual que antes).
- Si no hay `phones`, el flujo es idéntico al actual (validar email → create → save → addresses si hay).

### Compatibilidad
- La API no cambia: mismo body, mismos códigos 400/409/201. Solo se corrige la consistencia de datos.

## Patrones de Código a Usar

- **Validar antes de persistir:** Todas las validaciones que puedan fallar (y provocar 400/409) deben ejecutarse antes de cualquier operación de escritura que no se revierta con rollback.
