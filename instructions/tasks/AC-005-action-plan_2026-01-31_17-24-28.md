# AC-005 - ContactActivities: creación de actividad y búsqueda por contacto y tipo

## Descripción de la Tarea

Implementar el módulo de actividades (ContactActivities): (1) creación de una actividad asociada a un contacto, con activityType 'call' | 'meeting' | 'email', activityDate y description opcional; (2) búsqueda de actividades por contacto y tipo de actividad específico, retornando nombre, apellido, email y fecha de nacimiento del contacto junto con las actividades.

**Comportamiento actual:**
- Existe la tabla ContactActivities en el schema (AC-002) y el módulo de contactos (AC-003). No hay endpoints para actividades.

**Comportamiento esperado:**
- POST para crear actividad: body con personId, activityType ('call' | 'meeting' | 'email'), activityDate, description (opcional). 201 Created, 400 si validación falla, 404 si personId no existe.
- GET para búsqueda por contacto y tipo: query params personId y activityType; respuesta 200 con lista de actividades y datos del contacto (firstName, lastName, email, dateOfBirth).
- Verbos HTTP y status codes correctos; DTOs con class-validator.

## Criterios de Aceptación

1. ❌ Creación de actividad: POST con personId, activityType, activityDate, description (opcional). activityType solo 'call' | 'meeting' | 'email'. 201 con actividad creada, 404 si persona no existe, 400 si validación falla.
2. ❌ Búsqueda por contacto y tipo: GET con personId y activityType; 200 con lista de actividades y datos del contacto: firstName, lastName, email, dateOfBirth.
3. ❌ Validación de activityType: rechazar valores distintos de 'call', 'meeting', 'email' con 400.
4. ❌ activityDate y description según schema (TEXT; description opcional).

## Consideraciones Técnicas

### Performance
- Consulta de búsqueda por personId y activityType: la entidad ContactActivity ya tiene índices en personId y activityType (AC-002). Usar find con where o QueryBuilder; cargar relation person solo para los campos necesarios si se quiere optimizar.

### Seguridad
- Validación de entrada con DTOs (class-validator); consultas parametrizadas vía TypeORM. No exponer datos del contacto más allá de firstName, lastName, email, dateOfBirth.

### Casos Edge
- personId inexistente en POST → 404.
- personId inexistente en GET → 404.
- activityType inválido → 400 (ValidationPipe con IsIn o IsEnum).
- Búsqueda con contacto existente pero sin actividades para ese tipo → 200 con { contact, activities: [] }.
