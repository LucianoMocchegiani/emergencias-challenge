# feat(validations): agregar validaciones de formato para email y fechas

## Resumen

Implementa validaciones de entrada en DTOs para asegurar que los campos de email y fechas cumplan con formatos válidos antes de procesarlos. Afecta endpoints GET y POST de contactos y actividades.

## Motivación

Los endpoints aceptaban valores de email y fechas sin validar formato, permitiendo datos incorrectos que podían causar errores en procesamiento posterior. Este PR agrega validaciones usando `class-validator` para rechazar inputs inválidos con respuestas 400 claras.

## Criterios de Aceptación

- [x] GET /contacts/email: valida formato de email; devuelve 400 si inválido
- [x] GET /contacts (filtros): valida formato de dateOfBirth (YYYY-MM-DD) y email si se envían; devuelve 400 si inválidos
- [x] POST /contacts: valida formato de dateOfBirth (YYYY-MM-DD) si se envía; devuelve 400 si inválido
- [x] POST /activities: valida formato de activityDate (ISO 8601); devuelve 400 si inválido
- [x] GET by-phone: añade validación de formato para el número de teléfono

## Cambios Técnicos

### Backend (Node.js/TypeScript)

**Nuevos DTOs de query params:**
- `FindByEmailQueryDto`: valida email con `@IsEmail()` y `@IsNotEmpty()` para GET /contacts/email
- `FindByPersonalDataQueryDto`: valida filtros opcionales (firstName, lastName, dateOfBirth con `@Matches(/^\d{4}-\d{2}-\d{2}$/)`, email con `@IsEmail()`) para GET /contacts

**DTOs de body actualizados:**
- `CreateContactDto`: añade `@Matches(/^\d{4}-\d{2}-\d{2}$/)` a `dateOfBirth` (opcional)
- `CreateActivityDto`: reemplaza validaciones de `activityDate` por `@IsISO8601()` para formato ISO 8601
- `PhoneItemDto`: añade `@Matches(/^[\d\s+\-()]+$/)` a `number` para validar formato de teléfono
- `SearchByPhoneQueryDto`: añade `@Matches(/^[\d\s+\-()]+$/)` a `number` para validar formato en búsqueda

**Controller:**
- `ContactsController.findOneByEmail`: usa `FindByEmailQueryDto` en lugar de query param suelto; elimina validación manual
- `ContactsController.findAll`: usa `FindByPersonalDataQueryDto` en lugar de query params individuales

**Imports:**
- Añade `Matches` a imports de `class-validator` en DTOs correspondientes
- Añade `IsISO8601` y elimina `MinLength` en `CreateActivityDto`
- Elimina import no usado `FindByPersonalDataFilters` en `ContactsController`

### API / Rutas

**GET /contacts/email:**
- Antes: aceptaba cualquier string en `?email=`; validaba manualmente en controller
- Ahora: ValidationPipe rechaza con 400 si email no tiene formato válido

**GET /contacts (filtros):**
- Antes: aceptaba cualquier string en `?dateOfBirth=` y `?email=`
- Ahora: ValidationPipe rechaza con 400 si dateOfBirth no es YYYY-MM-DD o email no es válido

**POST /contacts:**
- Antes: `dateOfBirth` aceptaba cualquier string; `phones[].number` solo validaba `@MinLength(1)`
- Ahora: rechaza con 400 si dateOfBirth no es YYYY-MM-DD o si `phones[].number` contiene caracteres inválidos (solo acepta dígitos, espacios, guiones, paréntesis y +)

**POST /activities:**
- Antes: `activityDate` solo validaba `@IsNotEmpty()` y `@MinLength(1)`
- Ahora: rechaza con 400 si activityDate no es ISO 8601 válido

**GET /contacts/by-phone:**
- Antes: `number` solo validaba `@IsNotEmpty()` y `@MinLength(1)`
- Ahora: rechaza con 400 si `number` contiene caracteres inválidos (solo acepta dígitos, espacios, guiones, paréntesis y +)

## Notas Adicionales

**Formatos definidos:**
- `dateOfBirth` (contactos y filtros): YYYY-MM-DD (ej. "1990-05-15")
- `activityDate` (actividades): ISO 8601 (ej. "2025-01-15T10:00:00Z" o "2025-01-15")
- `phones[].number` (contactos): dígitos, espacios, guiones, paréntesis y + (ej. "+54 11 1234-5678")

**Compatibilidad:**
- Cambio breaking: clientes que envíen fechas en formato distinto (ej. DD/MM/YYYY) recibirán 400
- Recomendación: documentar formatos esperados en README o API docs

**Paso 5 implementado:**
- GET by-phone ahora valida formato del número de teléfono con `@Matches(/^[\d\s+\-()]+$/)`
