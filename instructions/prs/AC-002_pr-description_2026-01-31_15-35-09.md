# feat(AC-002): Proyecto NestJS + SQLite + schema (Person, Phone, PhoneType, Address, ContactActivities)

## Resumen

Se creó el proyecto NestJS con CLI, se configuró TypeORM con SQLite y se definieron las cinco entidades según docs/objetivo.md: Person, PhoneType, Phone, Address, ContactActivities. La app arranca con `npm run start:dev` y TypeORM crea las tablas en `./data/contacts.db` con `synchronize: true` en desarrollo.

## Motivación

AC-002 exige tener un backend NestJS funcional con SQLite y el schema completo para poder implementar los endpoints de contactos, teléfonos, direcciones y actividades (AC-003 a AC-007). Sin este paso no hay base de código ni tablas donde persistir.

## Cambios Técnicos

### Backend (Node.js/TypeScript)

- Proyecto NestJS creado con `npx @nestjs/cli new . --skip-git --package-manager npm --strict`.
- ConfigModule (@nestjs/config) global para variables de entorno desde `.env`.
- TypeOrmModule.forRoot() con SQLite: database `process.env.DATABASE_PATH ?? './data/contacts.db'`, entities por glob `**/*.entity{.ts,.js}`, synchronize en true (desarrollo), logging en development.
- Entidades TypeORM en `src/database/entities/`:
  - Person: id, firstName, lastName, dateOfBirth, email (TEXT).
  - PhoneType: id, typeName (TEXT).
  - Phone: id, number, personId, phoneTypeId; ManyToOne Person (CASCADE) y PhoneType (RESTRICT); índices en personId y phoneTypeId.
  - Address: id, personId, locality, street, number (integer), notes; ManyToOne Person (CASCADE); índice en personId.
  - ContactActivity: id, personId, activityType, activityDate, description; enum ActivityType ('call' | 'meeting' | 'email'); ManyToOne Person (CASCADE); índices en personId y activityType.

### Base de Datos (SQLite)

- Archivo de base de datos: `./data/contacts.db` (o DATABASE_PATH). Se crea al arrancar si no existe.
- Tablas creadas por TypeORM synchronize: person, phone_type, phone, address, contact_activities.
- FKs: phone.personId → person.id, phone.phoneTypeId → phone_type.id; address.personId → person.id; contact_activities.personId → person.id.
- Índices: personId y phoneTypeId en phone; personId en address; personId y activityType en contact_activities.

## Riesgos y Plan de Rollback

- **synchronize: true:** En producción no debe usarse; cambiar a false y usar migraciones TypeORM para evitar pérdida de datos por recreación de tablas. Rollback: restaurar backup de la BD si se pierde datos.
- **Dependencias transitivas (lodash, tar):** npm audit reporta 8 vulnerabilidades; no se ejecutó `npm audit fix --force` para no romper compatibilidad con Nest 11 y sqlite3. Documentado en para-mi-no-se-sube-a-github/repaso_paso_2. Rollback: no aplica a este PR.

## Notas Adicionales

- Tipos de texto en entidades: se usó `type: 'text'` en SQLite (no VARCHAR) porque SQLite no aplica límite de longitud; documentado en repaso paso 3.
- activityType: validación estricta en capa de aplicación (DTOs/servicios) cuando se implementen los endpoints; en BD la columna es TEXT con valores del enum.
