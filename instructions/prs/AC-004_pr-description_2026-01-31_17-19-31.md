# feat(contacts): Búsqueda por número y tipo de teléfono; soporte de teléfonos y direcciones en contacto

## Resumen

Se implementó la búsqueda de contacto por número y tipo de teléfono (GET /contacts/by-phone) y se amplió create/update de contacto para aceptar arrays opcionales de teléfonos y direcciones en el body. Un solo ContactsService usa los repositorios Person, Phone, PhoneType y Address; validación de phoneTypeId en create/update y en la búsqueda; status codes 200, 404, 400.

## Motivación

AC-004 exige la operación requerida por docs/objetivo.md: "Búsqueda de contacto por número y tipo de teléfono", y que los contactos puedan tener teléfonos y direcciones. En AC-003 no se incluían en create/update; este PR añade ese soporte y el endpoint GET by-phone sin CRUD separado de teléfonos ni direcciones.

## Cambios Técnicos

### Backend (Node.js/TypeScript)

- **Person (person.entity.ts):** Relaciones OneToMany con Phone y Address para JOINs y carga de relations.
- **ContactsModule:** TypeOrmModule.forFeature([Person, Phone, PhoneType, Address]) para inyectar repos de Phone, PhoneType y Address.
- **ContactsService:** Inyección de Repository&lt;Phone&gt;, Repository&lt;PhoneType&gt;, Repository&lt;Address&gt;. create: persiste Person y opcionalmente phones/addresses; validatePhoneTypeIds privado (400 si phoneTypeId no existe). update: reemplaza phones/addresses si se envían en el body (clave definida = reemplazo; omitida = no tocar). findContactByPhoneNumberAndType(number, phoneTypeId?, typeName?): valida number y al menos uno de phoneTypeId/typeName, resuelve typeName a id si aplica, query con phoneRepo (JOIN person), retorna Person | null. JSDoc en todos los métodos públicos.
- **ContactsController:** GET /contacts/by-phone con SearchByPhoneQueryDto; validación en controller de "al menos phoneTypeId o typeName"; 404 si contacto no encontrado.
- **DTOs:** PhoneItemDto (number, phoneTypeId), AddressItemDto (locality, street, number, notes opcional). CreateContactDto ampliado con phones y addresses opcionales (ValidateNested, Type). SearchByPhoneQueryDto (number requerido, phoneTypeId opcional entero, typeName opcional); Transform para phoneTypeId. UpdateContactDto sin cambios de código (hereda phones/addresses vía PartialType).

### Base de Datos (SQLite)

- Sin cambios en schema; se usan tablas Phone, PhoneType, Address ya definidas en AC-002. Person obtiene relaciones OneToMany; no hay migraciones.

### API / Rutas

- POST /contacts – Body puede incluir phones (array de { number, phoneTypeId }) y addresses (array de { locality, street, number, notes? }). 400 si algún phoneTypeId no existe.
- PATCH /contacts/:id – Body puede incluir phones y/o addresses; si se envían, reemplazan por completo. 400 si algún phoneTypeId no existe.
- GET /contacts/by-phone?number=&phoneTypeId= o &typeName= – Búsqueda por número y tipo (200 con contacto, 404 si no existe, 400 si falta number, si no se envía phoneTypeId ni typeName, o si el tipo no existe).

## Riesgos y Plan de Rollback

- **Reemplazo en update:** Si se envía phones o addresses en PATCH, se borran los existentes y se insertan los del body. Rollback: revertir commits de AC-004 si se requiriera otro comportamiento.
- **Validación phoneTypeId:** Create y update fallan con 400 si algún phoneTypeId no existe en PhoneType; asegurar que el catálogo PhoneType tenga datos o que el cliente envíe ids válidos.
